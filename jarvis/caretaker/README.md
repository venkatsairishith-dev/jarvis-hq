# Caretaker

Keeps the tools JARVIS is built from healthy: everything in `jarvis/tools/registry.json` and `jarvis/tools/jarvis.lock.json`.

## What it does
- **Finds issues** (`detectors.py`). Deterministic checks; no model is asked.
  - `upstream_release`: a newer GitHub release or tag, a changed Hugging Face file, or a newer Node.js release than the lock pins.
  - `advisory`: OSV advisories for the pinned PyPI packages (uv groups `jarvis` / `jarvis-dev` with their dependencies, the registry's pip tools) and the `jarvis/ui` npm lock. Only package names and versions are sent.
  - `lock_drift`: `fetch.py`'s own check of the files on one machine.
  - `test_failure`: failed and errored cases of the newest full benchmark v2 run.
  - `secret_scan`: gitleaks over JARVIS's own code (`jarvis/`, `jarvis/plugins/`; config `secret_scan_paths`), when gitleaks is installed. The vendored the face base is left to upstream. Only the rule, file and line are kept, never the secret.
- **Logs and de-duplicates** (`run.py`). A finding id is a hash of the tool, the kind and the key evidence. The same issue keeps the same id on every run.
- **Hands each new finding to the lab** as a kernel outcome task (task create, then lab dispatch, through the kernel's HTTP API). The `Idempotency-Key` is the finding id, so a re-run never makes a second task.
  - Only findings of severity `medium` or higher get a task, at most 5 per run.
  - Owner-only findings never get a task: a tampered file, a leaked secret, an asset replaced under the same tag. They are logged for the owner.

## How a finding becomes a pull request
1. The weekly scan (a lab task) runs `python3 -m jarvis.caretaker.run --config ...` in the lab.
2. For each new finding, it creates a task as the agent `caretaker` (public lane). The kernel always marks such tasks `source=caretaker`.
3. It dispatches the task to the lab. The instructions come only from `template.py`.
   - The kernel refuses a caretaker dispatch whose text does not pass `policy.caretaker_problems`: the template mark, the fixed rules verbatim, no merge or push-to-main clause, and only a `caretaker/` branch pushed.
4. The lab sub-agent works in this order:
   1. Clones the repo and creates `caretaker/<tool>-<id>` from `origin/main`.
   2. Records the old pin in the PR body and in `jarvis/caretaker/history.jsonl`.
   3. Changes only what the finding needs and runs the mapped tests and bench areas (`test_map.json`).
   4. Pushes its branch and opens a PR to `main`. When tests fail, it opens a draft or reports "could not fix".
5. An independent verifier in the lab checks the criteria. The kernel records the outcome.
6. The owner reviews and merges the PR himself, or closes it.

## What the sub-agent may and may not do
- **May:** clone, create its own `caretaker/` branch, change what the finding needs, run tests, push that branch, and open one PR (or a draft).
- **May not:**
  - push to `main`, force-push or merge;
  - enable auto-merge, or approve, close or edit other PRs;
  - change bench cases, rubrics or scorers to make a test pass;
  - put secrets or private data anywhere.
- Text quoted from outside (release notes, advisories, bench output, upstream names in the evidence) is in `~~~~untrusted` blocks. It is data, not instructions.
- The kernel's guard (`policy.caretaker_problems`) is an **allow-list over text, and still only text** (re-review M5, 2026-10-19). The dispatched instructions must be exactly the caretaker template (`template.py`) with only its fields filled in: a finding id `cf-<20 hex>`, a branch `caretaker/<slug>-<8 hex>`, a `https://github.com/<owner>/<repo>` clone URL, test commands that match the allow-list (a test runner on paths inside the clone, one bench case or area), and ONE free-text field (the suggested action) whose every plain word must come from a fixed vocabulary and which may not contain a branch or remote name, a publish/merge/release/sync/force/rebase/commit verb, a settings/Actions/workflow/secret/permission word, a shell, interpreter or downloader, an address, a path outside the clone, an encoded run, or any non-ASCII character. Everything from outside is in a quoted `~~~~untrusted` block (data, never an instruction). Anything the parser cannot place is refused; the older deny-list of verbs and commands runs afterwards as a second opinion. 42 reviewer paraphrases and 57 more are refused in every place they could ride (an extra step, the suggested action, a criterion), 30 ordinary tasks and all 88 registry tools are allowed (`jarvis/kernel/tests/test_caretaker_allowlist.py`). A change to `template.py` must be matched in `policy._ct_structure` (the tests fail until it is). A text check cannot stop a credential that can push.
- **Branch protection on `main` is NOT enabled and CANNOT be enabled on this GitHub plan** (verified read-only by the lead on 2026-10-19: the REST API answers 403 "Upgrade to GitHub Pro or make this repository public" for both branch protection and rulesets, and `branches/main` shows `protected: false`; the `gh` login on the server, config dir `/srv/jarvis/home/.config/gh-jarvis`, has the scopes gist, read:org, repo and workflow with admin permission on `jarvis-hq`). So the text guard above is the ONLY barrier for any lab agent that holds a GitHub token. See "Safe deployment" below: the lab agent must never hold a token that can reach `main`.
- The files that decide what leaves, what is checked and who may close a task (`gitleaks_gate.py`, `llm_proxy.py`, `scrub.py`, `owner.py`, `tasks.py`, `jobs.py`, `projectfix.py`, `lab_runner.py`, `control_auth.py`, and the existing `policy.py`, `audit.py`, `store.py`) are console-only to change: `policy.SAFETY_COMPONENTS` / `JARVIS_SAFETY_FILES` make an agent's write to them RED.

## Switching it on (owner, from the console)
1. Install the preset `jarvis/caretaker/automation_preset.json` through Automations: POST it to `/v1/jarvis/owner/automations`. It arrives **paused** and runs only after you press **Resume** on "Caretaker: weekly tool scan" (Mondays 03:17 UTC).
2. Issue the caretaker's token on the kernel machine, from `jarvis/kernel`: `python -m jarvis_kernel agent-token caretaker --lane public --out <file>`. Put that file where the lab worker can read it (mode 600). The token is never printed.
3. In the lab, create `~/.config/jarvis-caretaker/config.json` with:

   ```json
   {"repo_url": "<the jarvis-hq clone URL>", "kernel": "<kernel endpoint>", "token_file": "<token file>",
    "machine": "<lock machine name of the lab host>", "root": "<data root>"}
   ```

4. The lab's agent user gets a credential that **cannot reach `main`** (see "Safe deployment": a fork or mirror owned by a bot account, or a deploy key on that fork). It must not be the owner's `gh` login. Do this **before** step 1.

## How the lab's verdict is protected (audit M8, 2026-10-18; third pass after the independent re-review, finding H2)
**The problem.** The lab worker and the independent verifier run as the same OS user. Worse, the verifier is an agent session that *runs the worker's code* (the delivered tests), and that code runs as the same user too. Any process it forks can read the verifier's command line (it holds the verdict path and the one-run nonce), environment, file descriptors and working folder, and can write the verdict file. We proved this with a real forger (`jarvis/lab/tests/test_verifier_forker.py`). No secret, path, descriptor or file mode can stop a process of the same user, so the defence is built on things the checked code cannot touch.

**Why a third pass (re-review H2).** The second pass made the verdict *file* the thing to protect (root-owned folder, one pre-made file, inotify write counting, one read). An independent end-to-end test showed that is not enough: a second agent-user process opens `VERIFY.json` read-write, `mmap`s it and flips `"passed": false` to `true` (same length) in place; an `mmap` store produces no inotify event, and inotify coalesces repeated events, so it looks like the verifier's single clean write: `completed, passed=true`. Separately, the runner took the test count from the `Ran N tests` line the tests printed on stderr, so a "test" that printed `Ran 7 tests` and called `os._exit(0)` was recorded as 7 tests, exit 0. A file the agent user can still write can never be the proof, and text the tested code prints can never be the count.

**What is done now** (`jarvis/lab/lab_runner.py`, `jarvis/kernel/jarvis_kernel/{llm_proxy,tasks}.py`):
1. *Leftovers die first.* After the worker and again after the verifier, every process of the agent user started since the attempt began is killed (also after a normal exit), and an attempt whose leftovers cannot be killed is void. After the delivery the sweep runs once more; anything started or any changed file voids the result before "completed" is sent.
2. *The verifier's final answer is the authority.* The verifier must END with exactly one line `JARVIS-VERDICT: {one-line JSON}` (same nonce, task, job, attempt; `passed`; one row per criterion). Its stdout is captured by the runner into an unnamed file that only the runner owns (mode 600; the verifier gets a write-only, append-only descriptor; the runner reads through its own). `passed` and the criteria rows that go on come from that line (its sha256 travels as `verdict_channel_sha256`). No line, two lines or a line for another run is no verdict. When the runner is root, a process of the agent user can write that capture only through a descriptor it inherited from the verifier (re-opening it through `/proc/<pid>/fd` is refused by its owner and mode).
3. *The file is only a cross-check, frozen and sealed at the exit.* The slot is as before (fresh random folder, root-owned when the runner is root, one pre-made `VERIFY.json` written in place once, inotify write audit as a **secondary** detector). The runner holds its own read-only descriptor on that file's inode from the start. The moment the verifier process exits (before the sweep) it copies the file and the captured output once and seals the file (root-owned, mode 400, so no later open for writing succeeds). After every agent-user process is dead it reads both again, twice, and compares with the copies. A difference (a detached writer, a map held open across the exit), a disagreement between the file and the answer on `passed` or on any criterion's `met`, or a missing half, voids the attempt: it ends as an honest failure with the reason. The reviewer's `mmap` flip of an honest FAIL now ends `failed`, in both the keep-id and the container-root-with-`nobody` modes.
4. *The runner counts the tests itself, not from text.* The delivered files are read once; a separate, time-boxed process (60 s) only imports them and lists the test ids (importing runs module-level code, so it is isolated); a second process (180 s) runs exactly those tests through the `unittest` API under a runner-written harness that reports each test's start and stop to a pipe the runner holds. The runner (the parent) counts from those records and requires: the same ids in both steps; every collected test started and stopped once, in order; one final report as the last record whose totals equal the runner's own count; one process throughout (a fork that lets the original exit changes the process id); the harness's exit code; no process of the agent user left running afterwards (they are killed and the run is void); at least one test that really passed (zero tests or skipped-only is not a pass). Everything the tests print is captured and hashed but never parsed: `Ran 7 tests`, JSON look-alikes, `os._exit(0)` in the middle, `sys.exit(0)` at import, `kill -9` of itself, a segfault, a hang and a fork-and-exit all leave a gap or a contradiction and the run is void. The record (`trusted_execution`) carries the counts, `collected_ids_sha256`, `harness_sha256` (hash of the ids, per-test outcomes, exit code and totals) and the harness version.
5. *The kernel decides "verified".* A report is accepted only if it names the exact task, job and attempt the kernel dispatched and counted, the hash of the job's own criteria snapshot (not the task's current criteria), arrives while the task is being verified, and is the first for that (job, attempt) (a replayed, duplicated, late or other-attempt report is refused with 409). `passed: true` is stored only with a valid `trusted_execution` for the same artifact digest whose counts are consistent (collected = run = passed + skipped + expected failures, no failure or error, at least one pass, collection exit 0, no leftover process, a known harness version), **and** whose `harness_sha256` and `collected_ids_sha256` are the ones the verdict names, **and** a verdict that carries `verdict_channel_sha256`. An older runner (it counted tests from output), a record for another attempt, a wrong hash or a missing part is refused and the task fails honestly. If the delivered files contain no runnable tests the runner says `agent_assessed` and the task can only end "completed, NOT verified" (the screens already show that wording). The verifier's per-criterion rows must still cover every criterion, but they are the verifier's opinion.

**Behaviour you will notice.**
- A task whose deliverables contain no tests (a report, a document) can no longer be "verified"; it completes as "NOT verified" with the verifier's rows as advisory evidence.
- A verifier that writes its verdict twice, writes it by temp file and rename, prints no `JARVIS-VERDICT:` line, or prints something different from what it wrote, loses that attempt with a plain reason; the prompt says so.
- Delivered test files that run zero tests, only skipped tests, or leave a process behind no longer count as a pass. A test that stops its own process is not a pass. The delivered tests must be `unittest` style (`test*.py`); plain pytest functions are not collected (as before).
- The runner's record no longer says `python3 -m unittest`; it says `harness: lab-harness/1`. A lab box still running the old runner is refused by the new kernel (every pass is demoted) until it is updated: deploy both together.

**Fourth pass (2026-10-19): an isolation boundary** (`jarvis/lab/lab_isolation.py`, `lab_runner.py`, `tasks.py`; tests `jarvis/lab/tests/test_isolation.py`, `jarvis/kernel/tests/test_lab_report.py::RunnerContractIsolated`). The third pass could not close the same-user problems because every party ran as one OS user. Now:
- *Identities.* `jarvis-sandbox` runs **all** delivered / tested code. `jarvis-verify` runs the LLM verifier and owns the verdict file. The runner is root and owns the capture, the result pipes, the read-only copy of the deliverable and the harness script. The agent user (`agent`) still runs the worker. The runner reads `JARVIS_LAB_ISOLATION` (`auto` default, `identity`, `container`, `none`), `JARVIS_LAB_SANDBOX_USER`, `JARVIS_LAB_VERIFY_USER`, `JARVIS_LAB_VERIFY_BIN`, `JARVIS_LAB_VERIFIER_TOOLS`, `JARVIS_LAB_SANDBOX_IMAGE`.
- *Where the state lives.* Per attempt: `vstate-*` (root, 0711) holds the slot folder (root:verify-group, 0750, so the sandbox identity cannot even enter it) with the one verdict file (verify-owned, 0600; sealed root 0400 at the verifier's exit). `vview-*` (root, 0755) is the verifier's working folder: `deliver/` (copy of the exact bytes the runner will test, 0644, root-owned) and `EVIDENCE.md`. Nothing the sandbox identity can write is reachable from either; the tested code gets only its own scratch folder (sandbox-owned 0700, a fresh copy of the deliverable, deleted after the process).
- *How delivered code is started.* By a launcher the root runner executes (`LAUNCHER_SRC`): umask 077, every descriptor closed except 0/1/2 and the one result pipe, rlimits (CPU 120 s, address space 2 GiB, 64 processes, 64 files, 64 MiB file size, core 0), `setgroups([])`, gid and uid (all three ids), proof that `setuid(0)` fails, `no_new_privs`, then `exec` with an environment allowlist (PATH, HOME=scratch, TMPDIR, LANG, TERM, PYTHON flags). Any failure exits 126 and the run is void. stdin is `/dev/null`; stdout+stderr are a pipe the runner drains with a 64 KB cap; the result pipe is one extra descriptor.
- *How tests are counted.* One collection process (30 s), then **one fresh sandbox process per test id** (60 s each; chunks of ids above 200; 600 s per run), each with its own result pipe and scratch folder. The supervisor accepts a process only if its records are exactly the given ids, strictly shaped (exact keys and types, strict JSON: UTF-8, no duplicate keys, no NaN, shallow, 2000 bytes a line, 50000 records), in sequence, with one final record last and counts that match; if its exit status (from `wait4`, not from the process) is the one its own records imply; if it was not killed by a signal or the clock; and if no process of the sandbox identity outlived it (every process of that uid is killed after each step and any that was alive is a leftover that voids the run). The totals are summed by the supervisor; CPU and wall time are the operating system's. `harness_sha256` covers the per-id outcomes and exit statuses; the record carries the `isolation` block (mode, backend, self-test result, uids, process count, granularity, CPU seconds, reasons).
- *Self-test, before every verification.* The runner starts a stand-in process as the verify identity (holding the state file open, a secret in its environment), runs a probe as the sandbox identity and requires every check to be denied: list and open the state folder and file, create / rename / link in it, read the verifier's environ, memory, descriptors and cwd, `ptrace` it, signal it, open the runner's descriptors through `/proc`, regain root; and positive checks: groups empty, `no_new_privs` set, only `/dev/null` and pipes as descriptors, environment inside the allowlist, limits as configured. Any failure or error means mode `none`.
- *Modes.* `none`: no separation (not root, identity missing or shared, self-test failed, switched off): the tests still run (as the agent user, the third-pass harness) and the pass is kept by the kernel only as **completed, NOT verified**. `identity` / `container`: the tests ran separated and passed, but the **verifier's own tools are not known to run in a sandbox**, so its verdict is advisory: also **completed, NOT verified** (`assurance: isolated_tests_only`). `full`: separated execution **and** the owner has stated `JARVIS_LAB_VERIFIER_TOOLS=sandboxed` (its terminal backend runs commands as another user or in a container; **not checked for the installed Hermes, which is not on the Linux server**): the only mode the kernel will call **verified**. The kernel validates the whole record strictly (exact keys, types, sizes), the isolation block (sandbox uid is neither root nor the verifier's nor the runner's; self-test ok; mode consistent with backend and the verifier-tools statement; harness `lab-harness/2` for any isolated run, `/1` for none) and demotes anything else. The report and the screens show the mode and the reasons.
- *Fail closed.* Not root, a missing or shared identity, a failed self-test, an unknown setting, a missing container runtime: mode `none` with the reason, never `verified`. The keep-id arrangement of the Linux test server (one unprivileged user, no sudo) can never give separation; it runs the legacy checks and ends NOT verified. A final report the kernel cannot be reached for is retried (bounded) and the runner never reports success it did not deliver. At start the runner kills every process of the sandbox and verify identities and removes stale `vview-*`, `vstate-*`, `lab-sbx-*`, `harness-*` folders (a runner killed mid-attempt leaves them).
- *Container backend.* `container_command()` builds the rootless podman command (no network, all capabilities dropped, read-only root, `no_new_privs`, user namespace, pids / memory / cpu / fsize / nofile limits, a noexec tmpfs for scratch, deliverable and harness mounted read-only, the result pipe kept open with `--preserve-fds`). It is unit-tested at command-line level only. **The live container run is NOT RUN**: podman is not installed on the Linux test server and was not available inside the test container either; `spawn_sandboxed` raises for that backend and the fail-closed path is tested.

**What the boundary guarantees, and what it does not** (identity backend, root runner, real users; shown by `StateAttacks`, `ProcessShape`, `SandboxedTests`, `HandleLoopIsolated` in a throw-away container with `useradd`):
- Guaranteed against delivered code: it cannot read, write, truncate, map, rename, link or remove the verdict file or folder; cannot write the verifier's stdout, `/proc/<verifier>/fd/*` or memory, `ptrace` or signal it; cannot open any runner descriptor or read its memory; has no inherited descriptor but its own pipes; cannot regain privileges; is bounded in CPU, memory, processes, files and file size and by wall clock (a fork bomb, a 6 GiB allocation, a 200 MB file, endless output all end the run as void, and nothing of the sandbox identity survives a step); cannot leave state for the next test (fresh scratch each time, and, since the fifth pass, nothing it owns survives in the shared folders or System V IPC); cannot forge a record for any id but its own, nor change another process's exit status.
- A lying test **can** still do this: write a consistent record for **its own id** (it is then indistinguishable from a test that asserts nothing; pinned by `test_RESIDUAL_a_test_can_claim_its_own_id_passed_but_nothing_more`) and call the harness's own `emit` function to do it, because the harness runs in the same process as the test. It cannot do more than that.
- Not guaranteed: (1) anything against a kernel bug, a root compromise of the lab box or the runner, or a loose permission on a root-owned file; the boundary is OS-user separation inside one kernel, not a VM. (2) The sandbox identity can list the process table and read command lines (so the nonce is visible; the nonce alone writes nothing). (3) The verifier's own tool execution: if the agent CLI runs delivered code as `jarvis-verify` (the default for a CLI we did not configure), that code shares the verifier's identity, can inherit its stdout and flip its verdict file exactly as in the third pass (pinned by `test_RESIDUAL_code_the_verifier_runs_can_still_rewrite_the_verdict…`). That is why such a run can never be `verified`; with the owner's `JARVIS_LAB_VERIFIER_TOOLS=sandboxed` the claim rests on the owner's statement, which this repo cannot check. The read-only copy has no execute bit, but a file readable by an interpreter can still be run (`python3 deliver/x.py`): not enforceable, stated. (4) The runner could not run the verifier's session itself inside a sandbox: it needs the model API and its own configuration. (5) keep-id mode: nothing.

What the four **isolation modes** mean (the word on every report and screen): `none` = no separation (not root, an identity missing or shared, the self-test failed, or switched off): the tests still run, as the agent user, and a pass is kept only as "completed, NOT verified". `identity` = the delivered tests ran as `jarvis-sandbox` (root launcher, one process per test id) and the self-test passed, but the verifier's own tools are not known to be sandboxed: still "completed, NOT verified" (`isolated_tests_only`). `container` = the same with the rootless-podman backend: **command line only, podman is not installed on the Linux server, never run: BLOCKED**. `full` = `identity` or `container` plus the owner's statement `JARVIS_LAB_VERIFIER_TOOLS=sandboxed` **and** a verify identity of its own (fifth pass: without a verify user the verifier would run as the worker's user, so the statement alone no longer gives `full`): the only mode the kernel will call "verified". Podman alternative (`JARVIS_LAB_ISOLATION=container`, `JARVIS_LAB_SANDBOX_IMAGE=<python image>`): design only, `spawn_sandboxed` refuses it, the self-test says "NOT RUN", so the mode is `none`. Hermes (the real agent CLI) is **not installed** on the Linux server: whether it prints the `JARVIS-VERDICT:` line, writes the pre-made file in place and can run its tools as another user or in a container is unverified (**BLOCKED**), and so is any live verification on the lab box.

**Fifth pass (LAB-RT, independent red team + fixes, 2026-10-19).** Found by attacking the boundary from inside a real sandbox in a root container, fixed, each with a regression test that failed before (`jarvis/lab/tests/test_redteam.py`, `jarvis/kernel/tests/test_lab_verified_writers.py`):
- **Root followed links the worker could place (high).** `run_agent` opened its log (`work-2.log`, `verify-1.log`) with a plain `open(..., "w")` as root in the worker's folder: a symlink with that name, left by the worker in an earlier attempt, made the runner overwrite any root-owned file with the agent CLI's output (shown on a stand-in for `/opt/jarvis-hub/lab_runner.py`: it ended as the attacker's text). The job folder and the work root were `chown`ed through links the same way, the toolchain guard moved/rewrote files by path, and a verdict slot was made by path. Now every root operation inside the worker's tree walks the folder chain one component at a time with `O_NOFOLLOW` (a link not made by root is refused, a folder owned by someone other than root/the runner/the agent user is refused), files are created `O_EXCL|O_NOFOLLOW` relative to a directory descriptor, an old file or link under a log name is unlinked (never followed, never written through), and removals use `unlinkat`. The runner refuses to start when `~/work/jobs` is a link.
- **One test could prepare state for the next, and leave state on the box (medium).** Files in `/tmp`, `/var/tmp`, `/dev/shm`, `/run/lock`, `/dev/mqueue` and System V shared memory / semaphores / queues created by the sandbox identity survived the step (the old test for this only looked inside the scratch folder). After every step and before the next the runner now kills the identity and deletes everything it owns in those places and every System V object it owns (the removal is done by a process that becomes that identity: no extra capability), also for the verify identity after each verifier session.
- **A failing test could hide behind a passing one (medium).** A test whose `id()` returns another test's id made the supervisor run the real one twice and the failing one never ("2 passed"). Duplicate collected ids now void the run.
- **Tests in a group could answer for each other (medium).** A suite above 200 tests runs several ids per process ("chunk:N"); a test then reported a failing group-mate as passed and the run was accepted as `full` (shown with a 3-test suite and groups of two). A grouped run is now never `full` (runner `describe`, and the kernel refuses `full` unless the granularity is `id`): it ends "completed, NOT verified" with the reason. Splitting the suite into fewer than 200 tests (or raising `SANDBOX_MAX_PROCS` and the 600 s total) is the owner's/lab agent's call; measured cost is about 0.16 s per test process on the shared test server.
- **`full` without a verifier identity of its own (medium).** With no verify user the verifier ran as the worker's user, yet the owner's statement alone gave `full` and the kernel accepted it. `full` now needs a verify user distinct from the agent and sandbox users, in the runner and in the kernel (`isolation_problem`).
- Smaller: `1e999` passed the "no NaN/Infinity" parser as `inf`; a deliverable name ending in a newline passed the name rule (`$` before a trailing newline); `True` equalled the attempt number `1` in the verdict identity check; the verifier's session ran with umask 022 (now 077); a failing verdict could carry the kernel's own words `agent_assessed_pass` / `assurance` / `criteria_checked` / `kernel_check` / `isolation` into the stored record (the kernel now drops them from any report); delivered sandbox processes are now the OOM killer's first choice (`oom_score_adj` 1000); the self-test now also proves no capabilities remain and that the verify home and the runner token cannot be read by the sandbox.
- **Holds (attacked, nothing got through):** writing the verdict file / folder, opening runner or verifier descriptors through `/proc`, reading their environment or memory, `ptrace` and signals (different users, `ptrace_scope` is irrelevant), regaining root (`setuid(0)`, `su`, `passwd`, `mount`: the setuid programs are present but `no_new_privs` makes them inert; all capability sets are empty), raising a resource limit, supplementary groups, descriptors above 2 from the runner's parent and its environment (`env -i`), SysV and POSIX shared memory of the other identities (mode 600), Python start-up injection into the harness (`sitecustomize.py`, `usercustomize.py`, `conftest.py`, `.pth`, `PYTHONSTARTUP`, modules that shadow `unittest`/`json`/`os`, files in the sandbox HOME: none runs, the harness is `python3 -I -B`, no writable folder is on `sys.path` or `PATH`), writes to the harness script and to the read-only copy of the deliverable (write, rename, remove, link, chmod, create, also by the verify user), test ids with NUL / newline / `../` / 5000 characters / surrogates / non-strings (all void), early exits, forged records for other ids, oversize or duplicate-key records.
- **Residual, found and documented (not fixable without a namespace, which needs a capability the identity backend does not have):** the sandbox shares the lab box's **network namespace** with the runner and the verifier, so it can connect to any abstract unix socket and loopback port (pinned by `test_RESIDUAL_the_sandbox_shares_the_network_namespace...`); the runner and the verifier open none, but the Agent PC display (WSLg's abstract X11 socket, `jarvis-lab-control.service`) is one, guarded only by X authority. Egress for the two new users must be firewalled exactly like the agent's (the `jarvis-lab-fw.service` rules are not in this repository and were **not checked**). The sandbox can read `/proc/<pid>/cmdline` of other users (the nonce): `ProtectProc=invisible` in the unit (commented, untested) hides it. The sandbox can fill the disk within its limits (64 MB per file, no quota): availability, not integrity. The container backend (`--network=none`, tmpfs scratch) would close the first and the last; it is NOT RUN.

**What this still cannot stop (residual risk, plain words) WITHOUT the boundary, and what is left WITH it (see the lists above).** Everything below needs code that runs as the agent user, i.e. the worker's delivered code run by the verifier or by the runner's test run, or the verifier model itself. None of it is closed by anything in this repo; the real fix is one decision (below).
- **A forger that holds the verifier's stdout.** A process that *inherits* the verifier's own file descriptor 1 (a child the verifier tool started without giving it pipes of its own) holds a write descriptor on the capture file. It can truncate it and print a forged `JARVIS-VERDICT:` line, and flip the verdict file through a map, before the verifier exits; both halves then agree and the verifier's `passed` is forged. Agent CLIs normally give tool commands their own pipes, so this needs the verifier's tool layer to share fd 1, but nothing here enforces it and it is **not verified for the installed Hermes**. Pinned by `test_RESIDUAL_a_forger_that_inherited_the_verifiers_own_stdout_can_rewrite_both_halves` (fails the day the forgery is refused: update this text). Even then the task is "verified" only when the runner's own run of the delivered tests passed, so the forger can vouch for criteria the tests do not cover (for example "the report is correct") and can hide a failure the verifier found, but cannot make failing tests pass.
- **Same-user attach.** The verifier and anything it runs share one OS user. A process of that user can attach to the verifier (`ptrace`, `/proc/<pid>/mem`) and change its memory or what it prints when the kernel's ptrace policy allows it: always with Yama `ptrace_scope` 0, and for a still-running descendant of the verifier even with scope 1 (a double-forked process is no longer a descendant). Not checked on the lab box. The runner cannot see that.
- **The tests can attack their own harness.** The delivered tests run in the harness's process and OS user, so a test file that reads the pipe's descriptor number from its command line and writes a complete, consistent set of records (and exits) is believed: one test "passed" that never ran. The census of ids, the sequence numbers, the single process id, the exit code and the leftover check stop accidents, `os._exit` tricks and naive forgery only. Pinned by `test_RESIDUAL_a_test_that_writes_a_complete_fake_report_to_the_harness_descriptor_is_believed`.
- The worker can write tests that are trivially true (`assert True`); the runner's run then proves only that they ran to the end and passed. Only a human or a better verifier judges whether the tests are meaningful.
- Prompt injection of the verifier model through the files it reads is not an OS problem and is not addressed here. A verifier model that simply lies is not detected either (the tests are).
- The nonce and path are still on the verifier's command line (the agent CLIs take their task as an argument). They are not secrets any more: knowing them gains a forger nothing the final-answer authority, the cross-check and the kernel do not already check.
- If inotify is unavailable, no verdict is accepted (fail closed). The seal uses `chown`/`chmod` on the file's descriptor: if it fails the attempt is void. When the runner is not root (the keep-id test mode) the seal is a mode change the same user could undo, and the capture file can be reopened through `/proc`; the guarantees in the first residual bullet are only real with the runner as root and the agent as another user (the container-root tests with `nobody` check that).

**Owner decision (after the fourth pass, one question left).** The delivered tests are now separated; what is not is the verifier's OWN tool execution. Find out whether the installed agent CLI can run its commands as another user or in a container (for Hermes: a terminal backend that executes over SSH as another user or in docker/podman; UNVERIFIED, the CLI is not installed on the Linux server), configure it that way for `jarvis-verify`, and only then set `JARVIS_LAB_VERIFIER_TOOLS=sandboxed`. If it cannot, the answer stays 'tests verified in a sandbox, verifier advisory' (`completed, NOT verified`).

**Owner decision (third pass, now narrowed).** To remove these residuals the code the verifier runs, and the delivered tests, must not share an OS user (or a process namespace) with the verifier's own process and the runner's harness. Practical options: (a) run the verifier agent's *tool execution* in a rootless container or as a second OS user (for Hermes: a terminal backend that executes commands in a container or over SSH as another user; UNVERIFIED for the installed Hermes version), with only the delivered files mounted read-only and no access to the verdict folder or to the verifier's descriptors; run the runner's harness the same way (the tests as a third user, the harness records written by a separate supervisor process of the runner that the tests cannot reach); (b) run the whole verifier session as a separate user `verifier` that can read the workspace and write only the slot, and keep untrusted code out of that session by having the *runner* execute every runnable criterion itself (extend `trusted_execution` from the unit-test run to a per-criterion command list agreed at dispatch). Either needs a new OS user or container on the lab box, which the remediation was not allowed to add. Until then, treat "verified" as "the delivered tests pass under the runner's own harness, and the verifier's final answer agrees with them and with its file", not as proof against code that attacks the lab box.

**First live run (needs the lab box, not testable on the Linux server).** Run one trivial lab task and confirm: (1) the verifier can write the pre-made `VERIFY.json` in place (if the installed agent CLI writes files through a temp-and-rename, the attempt fails with "wrote no VERIFY.json" and the prompt or tool must change); (2) **the installed Hermes (`hermes chat -q ... --oneshot --quiet`) really prints the model's final answer, and only that, on stdout, so the `JARVIS-VERDICT:` line reaches the capture** (if it prints elsewhere, or reflows the line, every verification fails closed with "printed no JARVIS-VERDICT line"); (3) `jarvis/lab/tests/test_repair_loop.py` on the lab box passes; (4) `runuser` hands the harness its extra file descriptor (the container tests with `runuser` and `nobody` show it does on this image).

## The lab runner when the kernel is unreachable (audit M9)
While a worker runs, a kernel that does not answer (network blip, restart) never stops the work: this fail-open is deliberate, so a flaky link does not kill an hours-long job. The kill switch and the owner's cancel are checked every 5 s and take effect as soon as the kernel answers again. The outage and its end are now logged by the runner (`kernel unreachable ... fail-open by design`) and reported to the task as a note. The kernel's own model proxy is the opposite: it re-checks the kill switch before every provider, before a retry and between stream chunks, and stops.

## Logs
- Location: `<data root>/logs/caretaker/` (or `--log-dir`). It is never inside the repo; `run.py` refuses that.
  - `<date>/findings.jsonl`: every finding with the action taken (`task_created`, `task_exists`, `owner_only`, `below_threshold`, `deferred_max_tasks`).
  - `runs.jsonl`: one summary per run.
  - `seen.json`: the de-duplication state.
  - `cache/http.json`: upstream answers, kept for 6 hours.
- Every live run also appends `caretaker_run` to the kernel audit chain, with counts by kind and severity and the task ids it created.
- A refused caretaker dispatch is audited as `caretaker_dispatch_refused`.
- `history.jsonl` (in git, on each PR branch): `{time, tool, old_pin, new_pin, pr_url, finding_id}`. Helper: `python -m jarvis.caretaker.history add|set-pr|show`.
