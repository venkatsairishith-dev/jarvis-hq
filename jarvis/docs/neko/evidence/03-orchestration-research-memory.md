### 2.2 Cross-cutting evidence

- **LiteLLM supply-chain incident.** Malicious `litellm` 1.82.7 / 1.82.8 were on PyPI on 2026-03-24 for a few hours; 1.82.8 added a `.pth` file that runs at interpreter start; it stole SSH keys and cloud credentials [V ADK docs above; S https://www.netspi.com/blog/executive-blog/ai-ml-pentesting/litellm-supply-chain-compromise/]. LiteLLM is a core dependency of openhands-sdk, dspy, knowledge-storm (STORM), cognee, textgrad [V PyPI deps] and the route for ADK and II-Researcher. Anything pulled in here must be hash-pinned.
- **Small-model tool calling.** arXiv 2609.07370 (2026-09-07, single author, CPU benchmark, prompts that name the tool and all values): Qwen2.5-1.5B 75 % (greedy) / 79 % (sampling) tool-call success, Qwen2.5-0.5B 72 % / 32 %, Phi-1.5 0 %; "only 5 of 1,000 raw responses directly parseable as JSON" without a recovery parser [V abstract https://arxiv.org/abs/2609.07370]. An SLM survey argues schema adherence and validators matter more than parameter count [S https://arxiv.org/pdf/2510.03847]. llama.cpp: tool calls need `--jinja`; native handlers for Llama 3.x, Hermes 2/3, Qwen 2.5, Mistral Nemo, Functionary, Command R7B, GPT-OSS; other templates fall back to a "generic" format that "may consume more tokens and be less efficient"; aggressive KV quantization "can substantially degrade the model's tool calling performance" [V https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md]. llama-server supports schema-constrained `response_format` and `grammar` [V server README]. Already measured here: Ling-3.0-tiny with a grammar routes 11/12 correctly (03_DECISIONS D19) [L].
  - Implication [U]: every framework above assumes the model drives a free tool-calling loop. With 1.3-1.5B local models that loop is the weakest part; with Dahl (11 tok/s) every extra loop turn costs tens of seconds. `main_agent`'s single validated plan plus grammar-constrained JSON is the more reliable shape for this hardware.
- **Authority.** Every framework above brings its own approval / HITL mechanism (OpenAI SDK `needs_approval`, AG2 `hitl_hook`, LangGraph interrupts, MAF declarative MCP approvals). The kernel is the sole authority (CLAUDE.md, D15, D18). A second approval layer is a second authority; AG2's own advisory "keys both human-approval state and tool execution dispatch by tool NAME only" is an example of how that goes wrong [V gh].

### 2.3 Recommendation: keep `main_agent`, add four pieces (patterns, not dependencies)

Do **not** adopt a framework under `main_agent`. Its safety properties (plan-once from the user's words, closed catalogue, effect decided by code, held unknown steps, resume without re-run, two clocks) are not offered as a whole by any framework above, and each framework would add a second runtime and a second approval path. Record this in `01_RESEARCH_AUDIT.md` as the evaluation that the 2026-10-14 entry deferred.

Add, in this order:

1. **Typed run events for a real task timeline** (pattern: LangGraph `tasks` / `custom` stream modes and OpenAI SDK run-item events). Append-only `events` list in the run record, persisted with the checkpoint: `run.planned`, `step.started`, `step.progress` (free-form `{stage, done, total, note}` emitted by a dispatcher through `StepContext`, like LangGraph's `get_stream_writer()`), `step.waiting_approval`, `step.finished{outcome, seconds, attempts}`, `step.held`, `run.cancel_requested`, `run.finished`. The panel and voice read events, not raw state. Test: a fake dispatcher that emits three progress events produces them in order in the stored run file.
2. **Two cancel modes** (pattern: OpenAI SDK `cancel()` vs `cancel(mode="after_turn")`). Today only "after the current step". Add "now": cancel the asyncio tasks of running steps whose `effect == "none"` (think, read-only plugin entries, research); steps with side effects keep "after step" and, if interrupted after sending, are recorded `unknown` and held as today. Test: a 30 s think step is cancelled within 1 s; a non-idempotent step is never cancelled mid-flight.
3. **Grammar/schema-constrained planning on local models.** When the planner model is a llama-server model, send the plan JSON Schema as `response_format` (llama-server converts it to a grammar) so parsing never fails on syntax; keep `parse_plan` validation and the single corrective retry for Dahl. Test: 20 recorded planner prompts on Ling produce 20 parseable plans.
4. **A `research` plugin as a normal catalogue entry** (section 3). It plugs into `main_agent` as a plugin step whose entry id has no write verb, so `effect_of` classifies it as `none` (retriable, cancellable now). No new sub-agent kind and no new authority.

If a bounded inner loop is ever needed (for example a step that must call 2-3 read-only tools adaptively), use **PydanticAI** (MIT, 8 core deps, Chat Completions path with a custom `AsyncOpenAI` client) or the **OpenAI Agents SDK** (MIT, `chat_completions` mode, tracing disabled), inside one step, with only read-only tools, and with the kernel still deciding anything with an effect. Neither is needed for the work identified in this report.

### 3.3 Recommendation: port the pattern into one small `research` plugin; reuse the existing search plugin

No research repo fits as a dependency: the two maintained full apps (GPT-Researcher, LDR) need Python 3.12, bring 83-140 dependencies and their own web servers, and both had serious advisories in 2026; the LangChain reference is archived; STORM and MindSearch are stale; node-DeepResearch and Tongyi depend on third-party APIs or a model too big for the free disk.

Port these patterns (credited in the plugin docstring and in `01_RESEARCH_AUDIT.md`):

| Stage | Who runs it | Pattern source | Bound |
|---|---|---|---|
| 0. Lane check and query redaction | kernel policy + privacy redactor | existing | Queries leave the PC: public lane. Nothing from private memory goes into a query unredacted |
| 1. Plan sub-questions and queries | local general model, **grammar-constrained JSON** | local-deep-researcher; llama-server `response_format` | 2-4 sub-questions, <= 2 queries each |
| 2. Search | existing N.E.K.O `web_search` plugin (AnySearch -> DDG fallback, with its rate coordinators and cache) | reuse | <= 8 searches per run |
| 3. Fetch and extract pages | local httpx + readability-style extraction (reuse `utils/web_scraper` where possible); Jina Reader only as an optional fallback | II-Researcher scrapers | <= 8 pages, size cap, no JS rendering by default |
| 4. Select passages | BM25 over chunks per sub-question (no embedding service needed; N.E.K.O already has a BM25 tokenizer in `hybrid_recall.py`) | open_deep_research "compress"; II-Researcher compression | <= 12 passages, ids S1..Sn stored in the run record with URL and fetch time |
| 5. Notes and gap check | local model; JSON `{"done": bool, "next_queries": [...]}` | local-deep-researcher reflect step | <= 2 cycles |
| 6. Synthesis | Dahl through the privacy gateway (streamed) or local model when offline / private | GPT-Researcher publisher; STORM outline only for "report" length | every sentence must cite [Sn]; max output tokens set so Dahl finishes in about 2 minutes at ~11 tok/s [U] |
| 7. Verify | local verifier (HHEM-2.1-Open, or Jev if it measures well) on each (cited passages, sentence) pair | ALCE / FACT | unsupported sentences are marked "not verified" or dropped; the report states citation precision and lists sources with retrieval date |
| 8. Out of budget | forced final answer from what was gathered, labelled partial | node-DeepResearch "Beast Mode" | wall clock (default 6 min), search count, token budget |

Every stage emits `step.progress` events (section 2.3, item 1), so the timeline shows "searching 3/8", "reading 5/8", "verifying 14 sentences". Estimated size: 300-450 lines plus tests, all dispatch injectable like `local_team/core.py` [U]. Untested end-to-end time on this laptop: 3-6 minutes for a standard run [U].

### 5.5 Recommendation: one memory, three thin layers on top

No second memory system. Every framework in 5.1 brings its own extractor and store, and several need a strong structured-output model, a graph DB, or ship telemetry. N.E.K.O already has the pieces the frameworks sell (fact extraction with dedup, reflections, persona, evidence with reinforce/dispute decay, hybrid recall).

1. **Task memory = the run store, not a new memory.** `main_agent` run files already hold plan, steps and outcomes. Add one short, owner-visible "what was done" line per finished run, written through N.E.K.O's existing memory-server write path so it becomes an ordinary fact with a source tag. Research findings from the web are **not** written into persona or facts automatically: they are `external_content` (research/05 section 5.5; eTAMP and MINJA show one poisoned page can persist through memory). The run's sources stay in the run file and can be recalled by run id.
2. **Feedback = N.E.K.O evidence signals + the kernel corrections row.** Thumbs-up / correction on a run maps to (a) a reinforcement or disputation signal on the reflection or persona entry it used (N.E.K.O already weights direct user feedback differently, `memory-system.md`), and (b) the `corrections` row proposed in research/05 section 5.4 for plan-level lessons (wrong helper chosen, wrong mode). The planner reads open corrections for the task's category as a short block, the same way N.E.K.O injects user directives.
3. **Skill creation = plan templates through the existing skillgate.** After a run the owner marks as good, offer "save as a skill": a SKILL.md whose body is the validated plan (catalogue refs, goals, no secrets) plus the original request as an example. It goes to `staging/`, through `skillgate guard` and the owner's approval, never auto-activated (Voyager's library idea; the gate is the JARVIS part). The planner gets matching skill descriptions as hints; the plan is still validated against the live catalogue, so a stale skill cannot name a missing helper.
4. **Evals and optimisation offline.** Extend `jarvis/evals` with: planner cases (valid JSON, only catalogue helpers, step count, mode respected), research cases with recorded search results (citation precision/recall in the ALCE sense, scored by the local verifier), and memory-provenance cases. Run GEPA by hand against those cases with Dahl as the reflection model on synthetic or redacted cases only; adopt a new prompt only if `--baseline` shows no regression. Inspect AI or promptfoo only if a model-graded suite becomes necessary.
