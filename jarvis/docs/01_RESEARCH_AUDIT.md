## MetaClaw and the OpenJarvis quickstart (checked 2026-10-24, owner asked "can we use them")
Both were read from their public pages only (README / quickstart page). Nothing was installed or run.

**OpenJarvis (open-jarvis/OpenJarvis, Stanford, Apache-2.0, about 12k stars, 1,293 commits, no tagged releases listed).** The 2026-10-10 compatibility report above stands: improve JARVIS, never replace it.
- The quickstart is `curl -fsSL https://open-jarvis.github.io/OpenJarvis/install.sh | bash` (Windows: `irm https://open-jarvis.github.io/OpenJarvis/install.ps1 | iex`), then `jarvis init`, `jarvis ask`, `jarvis serve` (an OpenAI-compatible API on :8000), `jarvis model`.
  **Do not run it on the laptop**: the script comes from the docs site, not from a pinned commit; it installs uv, a venv, Ollama and a starter model; its README names no versions, and it describes no permission model for tools or agents ("code execution, file I/O, and shell access" in a preset). The 10-10 report found the runtime pulls in telemetry (posthog), a Rust extension and a Telegram library.
- Its command is also called `jarvis`, which would collide with ours.
- Its five parts (model/hardware choice, engines, agents, tools and memory, learning) overlap what JARVIS already has behind the kernel's approvals. Its learning loop is described only as "improves models using local trace data"; the one concrete command is `jarvis optimize skills --policy dspy`, which the 10-10 report already rejected (writes overlays automatically).
- **Use:** as a read-only reference and, if wanted, a trial **inside the lab VM** (never the laptop) pinned to a commit. Already reused: skill parser/types/tool translator (vendored), context-length helpers, the trace and eval patterns.

**MetaClaw (aiming-lab/MetaClaw, MIT, about 3.5k stars, v0.4.1 in April 2026).** A local proxy between an agent and its model that injects skills and memory into every turn, writes new skills from finished sessions, and can fine-tune LoRA weights from live conversations (RL).
- Fits: it works with any OpenAI-compatible client, names Hermes among supported agents, and its skills-only mode needs only an OpenAI-compatible endpoint (our gateway on 48950 qualifies).
- **Does not fit as it is:**
  1. It changes the prompt and writes skills **automatically**; our rule is propose, test, owner promotes, with one-step rollback (`SELF_IMPROVEMENT_2026-10-22.md`).
  2. It keeps its own memory in `~/.metaclaw/memory`; ours is the vault, and agents write only inbox/, daily/, decisions/.
  3. Its RL mode trains on **cloud** backends (Tinker, MinT, Weaver) with conversation data: private text would leave the PC. Not allowed.
  4. Its `start` edits the agent's config files and restarts services, installs a WeChat plugin when enabled, and reads Google Calendar when that option is on. No threat model is documented.
  5. Sitting in front of the gateway it would see text before redaction; behind it, it would see only redacted text and learn from placeholders.
- **Use, safely:** (a) its **built-in skill bank** (`memory_data/skills/`, about 40 `SKILL.md` files, MIT) can be imported through our existing gate (`skills/skillgate.py`: staged, hashed, owner promotes), which is the part of MetaClaw that fits without running it; (b) its idea of running learning updates only in idle windows is worth copying into our weekly lab tasks; (c) a skills-only trial in the lab VM on synthetic data, with its output turned into **proposals**, never live skills. Not recommended on the laptop or on private data.

**Decision:** do not install either on the laptop. Next step if the owner wants one: import MetaClaw's skill bank through the skill gate (a small, reversible job), and keep OpenJarvis as reference.

## Specialist roster (checked 2026-10-25)

Owner idea (D51 follow-up): a roster of small or mixture-of-experts specialists on the laptop, each best at ONE task kind, routed by task kind; an online provider only reasons over the specialist's output (for "what is on my screen": the best screen-reading model gives text or a description, the provider reasons). Budget (D50): 6.5 GB RAM for all of JARVIS, 2 GB of the 4 GB Radeon Pro 5500M, 3 CPU threads, models on D: only, one model loaded at a time (llama-swap), llama.cpp b11669 with Vulkan only, flash attention off on this GPU (`-fa off`). Nothing was downloaded or run; this is research from vendor pages and the llama.cpp source, all read on 2026-10-25.

**How to read this.** Every file size and licence is from the Hugging Face API/repo of the exact repo named (read today). Every benchmark number is from the page named beside it (model card, vendor blog, paper, or the Hugging Face leaderboard that mirrors a model repo's own `.eval_results`), and is the vendor's or author's own number, `verified: false` on Hugging Face, unless I say we measured it. Numbers from different benchmarks, or from different labs for the same benchmark, are not comparable. Speeds marked **[L]** were measured on this laptop earlier (in `MODEL_MATRIX.md`, `QUALITY_95_MODEL_BENCHMARK.md`, `llama-swap.yaml`, `evals/quality95/results/docreader-*.json`); everything marked **ESTIMATE** is my guess from those anchors and has not been run.

### 4. Which need a different quantisation or a CPU-only projector to fit 2 GB of VRAM

- Projectors (UI-Venus, Qwen3.5-2B, Qwen3-VL, MiniCPM-V, Granite-Vision): F16 file, `--no-mmproj-offload` (CPU). Do not use the BF16 projector on RDNA1. The Q8 projector of Qwen3-VL (0.445 GB for the 2B, 0.454 for the 4B) is a size saver in RAM; its accuracy cost is not measured.
- UI-Venus-1.5-2B: Q4_K_M is enough; the fit problem is the context (see above), not the quant.
- Qwen3-4B-Instruct-2507 (decider, tool_call): over 2 GB at `-ngl 99`. Fewer layers on the GPU. Q4_0 (2.376 GB) would not help; I have no tested lower quant, and a lower quant is a quality risk to measure first.
- OCR models: CPU only, as now (`-ngl 0`, projector on the CPU); VRAM is then not touched.
- MoE: nothing new. Ling already uses `--n-cpu-moe 16`.
- `-fa off`, `-t 3`, `--jinja`, `ttl: 120` stay as they are.

### 5. Cost of routing, and what this does not prove

- With one model resident at a time, every change of task kind is an unload and a reload from D:. The only measured number is LightOnOCR's first load at 15 to 25 s (`llama-swap.yaml`). A "what is on my screen" answer therefore costs, by my estimate, a model load, the image encode, the answer, and then the provider; I did not measure it.
- The repo's own earlier test found routing costs accuracy on text: routed specialists 37/44, Qwen3-4B alone 42/44 (`MODEL_PLAN_LAPTOPS_2026-10.md`). The evidence above says specialists win where a general model cannot do the job well (documents: ParseBench 74.6 for a 0.8B specialist against 35.4 for Qwen3.5-4B; GUI grounding: ScreenSpot-V2 92.8 against 85.6 for the base model it was fine-tuned from), and do not win on text. So the roster should be kept short: vision (1), documents (1), text decider + tools (1), chat (1), code (1).
- Because screen content stays on the PC (D51), a specialist that reads the screen and returns text still sends that text to the provider through the redactor; the gate and the untrusted-text rules do not change.

## mnfst/llm-gateway (Manifest), checked 2026-10-25 (owner asked "can we use this")
Source: the repository page https://github.com/mnfst/llm-gateway read today (MIT, about 7.6k stars). One OpenAI-compatible endpoint in front of 35 provider connections and 18 subscription flows; fallback to other models; `"model": "auto"` routing; local models (Ollama, LM Studio, llama.cpp); spend tracking and limits. It ships as a Docker image (`localhost:2099`), needs durable storage for request recording (S3-compatible or a persistent disk), and keeps full request and error bodies. The page does not mention caching, rate limiting or redaction/PII, and does not name its language.
**Decision: not adopted as JARVIS's gateway.** (1) Redaction is the job of `jarvis/privacy/gateway.py` (names and places hidden before anything leaves the PC); Manifest has none, and its full-body logging would store the owner's prompts. (2) Docker on the laptop does not fit the D50 budget (20% CPU, 6.5 GB RAM, D: only) next to the models. (3) What it adds (more providers, "auto" routing) is already covered by the gateway chain (per-provider cooldown, `max_concurrent`, `prefer_first` local model, pin file) and by the on-screen benchmark that picks the order. (4) Its "Gemini Free" option routes through Manifest's own managed key, a third party, and Google's unpaid terms allow training use and human review (https://ai.google.dev/gemini-api/terms). Could be reconsidered as a self-hosted router BEHIND our gateway on a server, never as the layer that sees unredacted text.

**Update the same day (owner: "or we can use OmniRoute as our endpoint on server"):** OmniRoute is the better server endpoint than Manifest, so the Manifest install is cancelled. Reasons: it is already on hermes-agent-vm (3.8.51, dedicated user, loopback only, API key required, 1500 MB cap, D4 trial), its unknowns are already known, and Manifest's are not (arm64, database, telemetry, client auth). Read today on https://github.com/diegosouzapw/OmniRoute: latest release v3.8.52 (19 Oct 2026); one published advisory, GHSA-hf57-cqmx-p4gr (ACP custom-agent RCE, Critical, 3 Sep 2026; affected and patched versions were not on the page read). Rule kept: it sits behind the laptop privacy gateway, public lane only (a config test refuses omniroute* outside the public lane); it holds provider keys, so it stays loopback/Tailscale only.

## Scouted tools: LiteParse fast path, ACE-style playbook deltas, pin refresh (2026-10-26, D67; custom code against existing projects)
Sources read on 2026-10-26: github.com/run-llama/liteparse (README, releases.atom: Python and Node v2.17.0, 2026-10-22), pypi.org/pypi/liteparse/json (2.17.0, wheel hashes, "This also installs the `lit` CLI command", no runtime dependencies listed), arxiv.org/abs/2510.04618 (ACE, v1 2025-10-06, v3 2026-03-29), github.com/kayba-ai/agentic-context-engine (Apache-2.0, README), github.com/microsoft/playwright-python/releases.atom (v1.64.1, 2026-10-22), pypi.org/pypi/playwright/json (1.64.1), github.com/CursorTouch/Windows-MCP (README telemetry section; releases.atom v0.8.8, 2026-10-10), pypi.org/pypi/windows-mcp/json (0.8.8, Python >=3.14).
- **LiteParse (reused, not rebuilt).** The existing digital-PDF reader is `doc_tools` (no OCR); the scanned-document reader is LightOnOCR through llama-server, which draws every PDF page and spends 4 to 11 s a page. LiteParse reads a page's text layer with PDFium (README: "Everything runs locally on your machine", no telemetry statement found on the page; the figure of 2 to 5 ms a page is the reel check, not measured here). Used as is, through its `lit` command with `--no-ocr`; nothing of it was copied. Custom code, and why: `plugins/doc_reader/fastpath.py` (about 190 lines) is only the glue that the kernel rules need and no library provides: the PDF goes in on standard input (the path rules of `check_path` cannot be sidestepped), a timeout and an output cap, a clean environment, "real text" test per page (at least 40 non-space characters, not garbled), per-page fallback to the OCR model, and the same `clean_page` cleaner as the OCR text. LiteParse's bundled Tesseract is NOT used (English data by default; Hindi and Telugu data "not found" on the page). Known difference: a text layer can hold text the eye cannot see (white on white), which the OCR path never read; the cleaner (`_shared/untrusted`, `scrub_text`) is applied to it and a test feeds it injected instructions, a card number, a key and direction-override characters.
- **ACE-style playbook deltas (method only).** The paper's abstract: contexts as evolving playbooks built by generation, reflection and curation with "structured, incremental updates", against "brevity bias" and "context collapse". The Kayba README (Apache-2.0) names an Agent, a Reflector, a SkillManager ("adds, refines, and removes strategies") and an optional embedding deduplication; its local-model support is not stated, so the library is not used. No code was read or copied. `plugins/desktop/lessons.py` already is the playbook store (D65); D67 changes its update path to items with helpful and harmful counters and a last_seen date, a `reflect` step that proposes `add / helpful / harmful / retire` and a deterministic `merge` that touches only the item a delta names. The reflector here is plain code over a content-free trace (no model, nothing leaves the PC); a small local model could one day propose deltas through the same `merge`, which ignores anything that is not made of closed words.
- **Pin refresh.** Version strings only, each re-read today: playwright-python 1.63.0 -> 1.64.1 (agent-venv.txt, node/requirements-browser.txt, the test Containerfile, registry); Windows-MCP benchmark pin 0.8.7 -> 0.8.8 with `ANONYMIZED_TELEMETRY=false` (README: default on, "Set to `false` to disable anonymous usage telemetry"). The Playwright pins are marked "from docs, verify on laptop" because the laptop venv was measured on 1.63.0 on 2026-10-23. Playwright MCP 0.0.83 was already the latest in the scout sweep and is not touched. No hash was changed: the only new hash is LiteParse's, read from PyPI.
